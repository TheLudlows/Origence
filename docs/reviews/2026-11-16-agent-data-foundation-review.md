# Origence · 首版架构检视与行业参考

审阅日期：2026-11-16。对象为架构 v0.7；处理结果已纳入[当前规划 v0.8](../design/agent-data-foundation.md)，
固定基线为 [5989040](https://github.com/TheLudlows/Origence/blob/5989040d2b714c948bd8bbf6f2bf4665032456be/docs/superpowers/specs/2026-11-16-agent-data-foundation-architecture.md)。
**结论：定位和首版分层合理，适合作为产品架构稿；补齐下列边界合同后再作为实施依据。**
用户已确认 R1/R3/R4 的处理规则，R2 收敛为归档/查询并排除工作现场恢复。R5–R7 仍单列为合同/验收改进建议。
本文记录审阅与处理决定，不代表新增能力已实现，也不扩展首版模块。

## 1. 应保留的决定

- 上下文包含记忆、知识、Skill 与运行状态；workspace 资产和私有会话分层。
- 全文与向量统一 AnySeek，Turso 保留权威状态与授权，Blob 保留原始工件。
- Skill 从记忆与执行经验形成候选，由有发布权用户批准后发布；发布不开放原始会话。
- Claude Code/Codex 本地 CLI、内网部署、研发与业务试点，以及最小运行追溯。
- 同一用户 key 共用同一平台会话作为首版默认；以下建议不自动改成多会话产品。

## 2. 四处边界与已确认处理

### R1 · P1：key、身份和会话生命周期（处理已确认，待实现）

位置：v0.7 第 3 节，90–93 行。使用稳定 `key_id` 而非密钥明文是正确起点，
但原稿未定义换密钥、撤销 key、共用 key 时会话归属和历史可访问性。
例如用户轮换凭据后，不能默认丢失历史，也不能因“同一用户名”自动合并本应隔离的 key 会话。

已确认：保留“一 key 一默认会话”的使用体验，区分逻辑 key 身份与可更换的凭据；独立新 key 默认独立，
若采用新的凭据记录，接续原会话须走明确授权。撤销凭据阻断访问，与删除会话、撤回支持来源分开定义。
会话与任务仍各有稳定 ID，客户端/逻辑 Agent 名称只作报告方信息，不自行授予访问权。
LangGraph 将 thread 与跨 thread 的记忆 namespace 分开管理；这支持分离标识的设计方向，
并不意味着用户必须采用 LangGraph 或放弃已经确认的默认会话规则。

### R2 · P1：仅归档/查询，工作现场恢复排除（已确认）

位置：第 3 节，91–104 行；第 7 节，179 行。
相同 key 能读取同一份 Origence 会话记录，并不能直接证明 Claude Code 与 Codex 的本地消息、
工具状态和上下文窗口已同步。当前四个 MCP 工具也没有实现完整的客户端会话导入/恢复。

已确认：Origence 会话只提供已提交记录的归档与授权查询；客户端原生聊天/上下文、工具/进程/环境现场恢复和操作重放均不纳入范围。
客户端来源标识可用于 `client_session_id → Origence session_id → run_id` 的追溯关联，不构成恢复入口。
同一平台会话可归档多个任务，但每次 Run 只读取适用内容并固定输入清单；不要加载全部永久历史。
两个客户端并发时需定义消息追加顺序/幂等、输入所见版本和任务状态更新条件，防止不同任务相互覆盖。
原生 Skill 的本地安装/缓存也要绑定 workspace 和加载清单，避免全局目录让另一 workspace 自动发现或加载。
平台撤回控制后续分发与受管加载；已经导出、离线保存或装入客户端上下文的副本，不能承诺服务端即时收回。
首版需要明确这一交付边界，不扩展为远程文件控制或 DRM 系统。

### R3 · P1：以选定审阅包批准共享（处理已确认，待实现）

位置：第 3 节，95–97 行；第 4 节，132–136 行。
“候选继承私有范围”与“另一发布角色可以审视候选”之间，仍需说明谁有权交付哪些内容。
拥有 workspace 发布权限，不应自动获得其他 key 的私有输入。

已确认沉淀流程为：读取获准私有输入 → 生成选定候选/脱敏依据 → 授权提交审阅 → 批准精确修订 → 发布 workspace 资产。
审阅授权覆盖该包，不开放原始会话；批准同时绑定正文、依据摘要、目标 workspace、版本与发布范围。
发布前再次检查读取/披露/发布权限及来源有效性，修改内容或目标范围后重新审阅。
此流程沿用既有候选/发布职责，不需要另建企业审批平台。

### R4 · P1：发布批准与工具执行权限分离（处理已确认，待实现）

位置：第 4 节，134–136 行。`SKILL.md` 可以包含客户端扩展，不能假定所有包都只是静态参考文本。
Claude Code 官方文档说明 `allowed-tools` 可预授权工具，动态上下文语法可在送入模型前执行命令。

已确认首版生成和分发仅包含文本指令、受控参考资料和允许的元数据；
发布器按指定客户端版本验证允许字段，拒绝生成候选中的工具预授权、hooks、动态命令与可执行脚本扩展。
Skill 不携带凭据；正常工具操作继续服从执行端与用户授权。用户批准共享方法，不等于批准方法涉及的所有动作。
这是现有 Skill 分发的边界约束，不是增加沙箱或工具执行平台。

## 3. 三处可直接沿现有能力收紧的设计

### R5 · P2：共享记忆需要保留事实状态和适用条件

位置：第 3 节，73–81、95–100 行。“workspace 持有”描述归属，不表示其中所有陈述对所有任务都正确。
例如“项目 A 测试环境是 X”不应覆盖同 workspace 中项目 B 的配置；用户猜测也不因沉淀就变成确定事实。

建议在精简稿中明确回指已有[身份与上下文规则](../contracts/memory-identity-and-context.md)和
[S2 合同](../contracts/memory-semantics.md)：主体/属性/条件、来源、事实状态、版本条件与冲突证据继续生效。
这些已有实现基础，属于补充约束引用，不要求新建通用真值判定或另一套记忆系统。

### R6 · P2：Skill 的可读性、触发正确与任务收益要分别验证

位置：第 4 节，123–136 行；第 7 节，180、187–188 行。
“人批准了”“客户端加载了”与“方法改善了任务结果”是不同证据。

建议直接采用 Agent Skills 的标准元数据与逐步加载方式：先提供名称/描述，选中后加载正文，参考资料按需读取。
首版用少量冻结的适用任务和不适用反例，分别检查是否正确选择、步骤是否有效、输出是否支持目标。
同模型/工具条件下比较启用与未启用 Skill 的结果，保留内容摘要、客户端版本和人工修正。
沿用现有[效果评估标准](../Origence_效果评估与对比标准.md)，无需新建评测平台。

### R7 · P2：将最小运行记录明确纳入第一步验收

位置：第 7 节，179–183 行。正文已说明 Run 随接入逐步补齐，但表格可能被理解成第二步 Skill 先做、第三步才有运行依据。

建议第一步同时验收最小 `session_id/run_id/event_id`、输入清单、结果/反馈与采集缺口，第二步以这些记录提炼 Skill；
第三步完成统一追溯界面。事件传播与来源关联可以借鉴 Langfuse/LangSmith，不引入完整 APM。
AnySeek 替换的验收同时复用既有过滤/发布合同：全文与向量均在 top-k 前约束可见候选、返回前复核权限/来源/版本，
双检索面保持同一有效版本，故障不伪装空结果；真实后端验证通过后清理 LanceDB 检索依赖。

## 4. 官方参考及适用边界

以下为检索日查阅的代表性产品/标准，不作“最先进产品”的统一排名，也不把其文档当作 Origence 的运行验证。

| 来源 | 可借鉴的机制 | 对 Origence 的取舍 |
| --- | --- | --- |
| [LangGraph：Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | thread 状态与跨 thread store 分离 | 保留私有会话与 workspace 资产分层，补生命周期与任务上下文选择 |
| [LangMem：Core Concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/) | 事实、经历和程序性记忆分开组织 | 明确经验记录与可复用方法的转换，不把所有事实直接变成 Skill |
| [Letta：Skills](https://docs.letta.com/configuration/skills)、[Shared memory](https://docs.letta.com/concepts/shared-memory) | 将完成过的工作提炼为 Skill；区分 Agent 与组织共享内容 | 支持经验到方法的方向；采用 workspace 发布边界，保留人工批准，不引回 Git 协作范围 |
| [Agent Skills 规范](https://agentskills.io/specification) | 标准包格式及元数据/正文/资源逐步加载 | 复用通用格式，客户端扩展需明确控制，不能仅凭文件名认定兼容 |
| [Claude Code：Skills](https://code.claude.com/docs/en/skills) | 原生加载、客户端扩展和 Skill 基线比较 | 明确方法发布与执行授权的边界，真实客户端验证仍独立进行 |
| [OpenAI：Build skills](https://learn.chatgpt.com/docs/build-skills) | Codex 支持按名称/描述发现，再加载完整指令 | 双客户端适配保持共同语义，具体能力按已选版本核验 |
| [Langfuse：Sessions](https://langfuse.com/docs/observability/features/sessions)、[LangSmith：Threads](https://docs.langchain.com/langsmith/threads) | 用会话 ID 关联多次 trace/run，并传播关联标识 | 保留最小 Run 和事件关联；观测聚合不等于原生会话恢复或完整采集 |

## 5. 处理结果与后续入口

四项处理决定已纳入 v0.8：明确逻辑 key 生命周期、排除工作现场恢复、选定审阅包共享、发布/执行授权分离。
实现仍须固化相关合同与验收；R5–R7 继续作为既有合同/验收的优化建议。保持三个核心闭环和已确认的数据归属政策。
本次检查覆盖架构稿、相关领域合同、现有 MCP/会话入口和官方资料；没有执行客户端、AnySeek 或生成模型验证。
