## 正确证据诊断

冻结 [配置](freeze.json)后，以相同 qwen3.8-flash、ANSWER prompt、温度 0、关闭额外推理，只向阅读器提供每题全部金标准来源，进行 28 次调用，记录 8735 total token。[完整结果](oracle-report.json.gz)：开发 12/12、原新主题 16/16 通过旧短语和必要引用代理，无可答题拒答。7 个无答案题排除，因为向其提供空的金标准上下文会让拒答变得不真实地容易。

这是离线诊断，不是可部署检索；金标准仅在此工具中选择来源，参考答案/标签不送入模型。模型看到原文元数据和文本，不看到 diagnostic-only ID。与历史 Answer 的比较是一次新推理与旧推理的探索性对照，不能当确定性因果收益。

**不得写成 28/28 语义正确。** 同一 agent 逐题检查发现 orchestra-q6 把严格低于 82 dB 写成不能超过 82 dB；workshop-q11 的“18 摄氏度以下”未明确保留严格性。旧问题本身也存在诱导非严格边界的措辞。详见[语义复核](oracle-semantic-audit.json)。不改历史标签，新的 [v4 成对反例](../v4/README.md)要求显式判断恰好等于阈值是否合格，并保留可答正例和缺事实负例。

## 本地模型环境

本机 Intel i5-14600KF / 32 GiB RAM / RTX 5060（8151 MiB），现有 Python 3.10.20 + torch 2.7.0+cu128 可使用 CUDA。项目 target 下建立带 system-site-packages 的 venv 复用 Torch，其余固定依赖安装在项目目录，未修改原环境；这是本机复用配置，不声称独立环境可完全复现。依赖见 [requirements](../../../tools/requirements-aml-rerank.txt)。系统 requests 的可选字符检测版本发出兼容告警，不把它记录为模型质量失败。

官方 BAAI/bge-reranker-v2-m3 固定 revision 953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e；[文件清单](reranker-model.json)包含精确大小和 SHA-256。模型/缓存只在 target，不进入 Git。官方 snapshot_download 在本环境缺少远端 metadata 而失败；改用官方固定 resolve 地址流式下载，校验实际字节数和 LFS SHA-256。未启用 remote code。

现有 GPU Python 为 3.10，初次脚本在 hashlib.file_digest 处启动失败；共享 SHA-256 改用 1 MiB 分块的等价实现，覆盖压缩前原始哈希。其次因继承环境 SciPy 二进制接口不兼容而导入失败，[失败报告](reranker-load-failure.json.gz)及[处理记录](compatibility-revision.json)保留。Oracle 调用发生在兼容性修改之前，原 helper 源码保存在 source-at-oracle；提示词、语料和评分均未调整。

## 专用重排实测

固定配置完成 35 题 / 3500 个 query-passage 对的 GPU 推理；[完整工件](reranker-report.json.gz)、[预运行配置](reranker-freeze.json)。每对最长 512 token，实际无截断，float16，batch=8。40 候选的排序从相同的逐对分数取子集；仅测了每题 100 对的推理耗时，没有伪造 40 对耗时。

| 策略 | 开发 Recall@5 / 完整证据覆盖 | 原新主题 Recall@5 / 完整证据覆盖 |
| --- | --- | --- |
| 原 vector | 79.17% / 66.67% | 63.54% / 56.25% |
| 历史聊天重排（40 候选） | 91.67% / 83.33% | 95.83% / 93.75% |
| 本地 BGE 重排（相同 40 候选） | 75.00% / 66.67% | 83.33% / 75.00% |
| 本地 BGE 重排（100 候选） | 75.00% / 66.67% | 83.33% / 75.00% |

扩大输出到 20 条时，BGE 在原新主题 100 候选中完整覆盖 16/16，开发仍为 8/12。这是增加证据数量的探索观察，未控制同一阅读器 token 预算，不能据此宣称比聊天重排更优。原始逐对相关性排序会遗漏间接桥接事实，也受相似重复干扰影响；没有用 gold 修改模型输入、阈值或重排结果。

每题 100 对推理 p50：开发 298.18 ms、原新主题 299.05 ms；p95：887.32 / 303.75 ms。开发包含本次首次推理的 887.32 ms；模型加载另耗 3319.31 ms。GPU allocator 峰值 allocated 1164659200 bytes、reserved 1191182336 bytes，均不包括其他进程或主机 RAM。模型只加载一次、串行无负载测试，不是 Search 端到端 p95 或 SLO，也不能直接与历史聊天检索链路 p95 相减计算收益。

阶段判断：该配置运行快，但相同候选与 top-5 下的证据质量未追上聊天重排，不能直接替换。先保留已测聊天方案作为质量对照，本地 BGE 作为成本候选。查询深度/证据预算仍需新数据验证，不能仅为修复几道旧题增加规则。

## 专用重排的 Answer 代理

查看检索结果后追加探索性比较，固定与历史相同的 ANSWER prompt、聊天模型、40 候选及最多 5 条原文证据；未根据 gold 选择上下文。35 次模型调用、21420 total token，全部完成。[原始结果](reranker-answer-report.json.gz)与[调用前配置](reranker-answer-freeze.json)。

| 方案 | 开发可答代理成功 / 无答案拒答 | 原新主题可答代理成功 / 无答案拒答 |
| --- | --- | --- |
| 历史 vector | 8/12 / 3/3 | 9/16 / 4/4 |
| 历史聊天重排 | 10/12 / 2/3 | 15/16 / 4/4 |
| 本地 BGE 重排 | 8/12 / 3/3 | 12/16 / 4/4 |

BGE 的可答题拒答为开发 2/12、原新主题 4/16；开发仍错误回答相似活动的 25℃。它改善了这次序列号无答案题的拒答，但没有同时保住聊天重排的可答成绩。故目前保留聊天重排作质量对照，本地模型作成本候选，不直接接入产品。此次 Answer 为事后追加且仍用旧代理，不能声称已完成新冻结语义验收或可靠拒答。两次本轮聊天实验合计 63 次调用、30155 个供应商报告 token，未换算货币费用。
