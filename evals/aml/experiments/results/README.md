# 受限检索策略实验 · 2026-10-11

开发集、新主题测试和答题代理分别报告。模型为本地 BGE-M3 1024 维及已授权 qwen3.8-flash 网关，enable_thinking=false、JSON 模式、温度 0。代码与参数见[策略冻结](../freeze.json)，所有失败尝试保留，业务 Rust/API 尚未改变。

## 开发集 Answer 代理

[固定答题输出](development-answer.json.gz)完成 30 次模型请求。可答题要求参考短语匹配且引用全部必要来源：vector 8/12，扩展重排 10/12；可答题拒答分别 2/12 和 0/12。无答案正确拒答却从 3/3 降到 2/3。

扩展重排仍在 workshop-q4、q11 把其他活动的 25℃当作目标样机温度；workshop-q12 把返修工单 IR-7306-B 当成设备序列号。说明候选覆盖改善没有自动带来语义区分和可靠拒答。现阶段不将该策略接入生产 Search。下一步应先做事实类型/实体范围与下游拒答验证，不能只追求 Recall。代理指标不是完整语义评审，原始答案仍需人工检查。

## 接入可靠性与迭代边界

保留初始策略失败、两次请求失败、两次对象格式失败及新测试的两次包装格式中断。JSON 模式仍可能出现列表、索引对象列表或单层对象包装；适配器仅做有界结构归一化，正文若出现必须与候选逐字一致，始终返回原始候选。错误名称 modified_selection_evidence 在两个中断工件中也覆盖“缺失 index/content”的情况，不代表已观察到正文被恶意改写。

新测试重跑仅修复输出结构适配，没有改变题目、标签、提示词、模型模式、查询数、候选数或排名方法；仍必须披露已发生中断和重复调用，不能宣称是一次无故障的未见测试。温度 0 仍产生不同 JSON 包装，不能保证供应商确定性。

## 当前决策

该候选策略保留为实验工具，暂不接入核心 API。下一步优先验证实体/活动范围和事实类型（如工单号不能代替序列号）、证据不足时的拒答，再做延迟控制。任何新增提示词或策略使用新的冻结测试集验收；先同时满足可答题证据完整性与无答案拒答，才考虑产品实现。

## 新主题测试（v3，适配修复后的完整重跑）

| 策略 | Recall@5 | 全部必要证据覆盖 | 无答案非空候选 | p95 检索耗时 |
| --- | ---: | ---: | ---: | ---: |
| vector | 63.54% | 56.25% | 4/4 | 408.28 ms |
| 只重排 | 95.83% | 93.75% | 2/4 | 1554.85 ms |
| 扩展 + RRF | 45.83% | 43.75% | 4/4 | 未单独计时 |
| 扩展 + 均衡候选 + 重排 | 97.92% | 93.75% | 1/4 | 3913.75 ms |

16 可答、4 无答案。[原始记录](new-topics.json.gz)含 60 次聊天调用、157467 token。没有使用测试标签调整查询/排序策略；修复两种输出包装后完整重跑，因此应描述为冻结新主题的回归测试，不能宣称一次无中断的完全未见验收。数据仍是同一 agent 编写，未独立人工复核。

只重排和扩展重排的完整证据覆盖相同，前者 p95 较低；因此追加只重排的 Answer 对照作为探索性分析。该扩展比较是在查看检索结果后决定，答案提示词和参考保持不变，不把它描述为预注册结论。

[新主题答题原始记录](new-topics-answer.json.gz)共 60 次调用、25711 token；[开发集追加只重排](development-rerank-answer.json.gz)15 次调用、4863 token，得到可答题 10/12、拒答 1/12、无答案正确拒答 2/3。开发集原双臂 Answer 为 30 次调用、13851 token。

只重排与扩展重排在两个集合的答题代理成功数相同，前者模型调用少、检索延迟低，因此作为下一轮的优先候选。这里的只重排答题比较属于探索性追加，不能当预注册统计结论。业务接口继续保持原始 vector；开发集的错误拒答/事实混淆仍阻止推广。

新主题共同失败为 orchestra-q0：三跳链需要维护人、门店、营业地址，扩展后仍缺一条，Answer 正确选择拒答。已逐题核对本轮只重排答案与原文，但不是独立人工复核。参考短语指标只核对如“82”的数值，不能验证“严格低于”与“不超过”的边界差别，也不能覆盖所有额外陈述；不要把 15/16 称作正式语义准确率。
