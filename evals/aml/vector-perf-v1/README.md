# 向量查询定位与显式停机压实

基于 main 6a609d3，2026-10-11。正式检索继续使用精确向量查询、原有候选批次和完整权限/来源复核。新增 vector_timing 聚合计时与 --offline vector-compact 维护入口；没有接入重排、回答或聊天裁判。本轮没有聊天模型调用。

## 排除无效优化

同一个隔离库含已观察公开最长历史 46 批/502 条消息及其他四个用户的 512 个单消息批次。基线 → 列投影候选 → 基线复测各 8 次 Search，top-k 5/100 交替，所有返回 ID、内容、元数据和顺序完全一致，原文字节/scope 校验通过。

[同库运行](run.json)的 HTTP p50 为 2203/2230/2215 ms；候选与复测重启后的首请求分别约 4125/4088 ms，全部保留。基线每个 Search 的两次 native 查询累计：打开表约 7.70 ms，规划/启动约 321.54 ms，结果流执行/读取约 1689.44 ms。不能把 collect 全部归为磁盘等待，但足以排除“打开表是主要瓶颈”的假设。

列投影只返回 ID/source/version，距离仍由库计算，结果完全一致却没有明显性能收益，故已撤回。两份受测 Rust 实现快照保留为 baseline-lancedb.rs.gz / projection-lancedb.rs.gz；[预登记候选](candidate-plan.json)及[汇总](summary.json)保留，不把失败方案当作已上线优化。

## 物理布局对照

[原生实验](layout.json)在自身临时目录内使用公共 VectorStore 和 LanceDB API：563 个允许候选分 47 批写入，另 512 次外部 workspace 写入更近的干扰向量；共 1075 行、1024 维、559 个碎片。只执行 Compact，两个任务、目标每片 4096 行，不执行 All/Prune。

压实 373 ms，559 个碎片变 1 个，1075 行保持不变。8 个向量/limit 组合在压实前约 2.02–2.09 秒，压实后约 0.41–0.43 秒，重新打开连接后约 0.41–0.44 秒；24 次结果的 ID、source、score、排序与 scope 预期完全一致。数据量相同而物理布局变化带来显著改善，支持小文件碎片是本场景的主要成本之一。

这是合成向量、debug 构建、原生存储测量，不是 HTTP 性能或语义质量成绩。首请求保留；没有并发写入、峰值内存或强退/断电验收。执行器 examples/vector_layout_probe.rs 只能创建自己的临时目录，不能指定业务数据库路径。[运行前计划](layout-plan.json)。

## 实施取舍

采用显式停机压实，不增加在线后台任务。命令必须带 --offline，并复用 context.db 的非重入 OS 锁；先以只读连接验证现有关系库，再验证所有向量表的命名及完整 schema，之后逐表压实。CLI 只做参数与分发，库 API 为 storage::maintenance::compact_vectors。无模型、子进程或内部 CLI 重入。

非重入锁会拒绝同进程后来的普通 open，普通 API/Worker 的重入共享仍然保留。dry-run 不改变向量版本。压实不更改模型/profile、原文、locator、parser、授权、scope、generation、ID、候选预算或距离算法，保留旧版本。每表独立提交，失败可部分完成；不宣称跨表原子性、硬内存限制或硬取消。详见[运维说明](../../../docs/OPERATIONS.md#显式停机压实向量文件)。

依据使用固定依赖 lancedb 0.23.1 的官方 Compact API 与本地相同版本源码；[官方 API](https://docs.rs/lancedb/0.23.1/lancedb/table/struct.Table.html#method.optimize)区分合并碎片与清理历史版本。本次没有升级依赖或修改 Cargo.lock，也不默认创建标量/向量索引。

## 真实 CLI / HTTP 对照

[执行前计划](maintenance-plan.json)、[32 次原始记录](maintenance.json)、[汇总](maintenance-summary.json)。相同最长公开历史及 512 个外部批次，通过真实本地 BGE-M3 和 Add/Search 建库，再依次基线、停机 dry-run、停机压实、再次重启，每阶段 8 次，top-k 5/100 交替。

| 阶段 | HTTP p50 / p95 (ms) | vector p50 / p95 (ms) |
| --- | --- | --- |
| 基线 | 2247.79 / 2348.88 | 2067.08 / 2152.69 |
| dry-run 后重启 | 2215.76 / 3985.38 | 2068.11 / 2680.46 |
| 压实后重启 | 644.13 / 1848.29 | 473.65 / 498.38 |
| 再次重启 | 623.94 / 1779.17 | 454.31 / 499.28 |

分位数用 nearest-rank，包含每阶段首请求；每组仅 8 次，因此 p95 等于最大值。冷启动约 1.8 秒仍然存在，主要在其余检索处理阶段，不能宣称所有请求低于一秒。压实 HTTP p50 比基线降低约 71.3%，但只是这一已观察历史的局部对照。

实际 CLI 在活跃宿主下拒绝执行，停机 dry-run 不改版本；压实耗时 2272.10 ms，将 558 个碎片合为 1 个，1087 行不变，版本 559 → 561。所有 32 次完整 data 内容、ID、元数据和顺序相同，原文字节及 scope 检查通过。两次 HTTP 实验与原生实验均使用自身临时库并完成清理；没有对用户业务库执行维护。历史版本可读的直接验证来自 Rust 回归测试，HTTP 工件不冒充历史版本验收。

运行命令与工件 SHA-256 见 [manifest](manifest.json)。

后续优先在更大多用户/多 profile 数据、持续写入和维护中断场景验收，再讨论维护周期；本轮仍未重跑完整 32 用户公开库约 5.29 秒场景。生产 SLO、强退/断电、磁盘不足、独立人工标签与官方 Smoke/Full 均未因此完成。服务和域名继续后置。
