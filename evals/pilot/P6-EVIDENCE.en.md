# P6 independent sign-off and Run verification evidence

**English** · [简体中文](P6-EVIDENCE.md)

Use one restricted evidence bundle per case and Run. Use the [blank linkage record](p6-case-link.template.json) for case ID, scenario, client, baseline/reuse arm, and Run. Follow the [runbook index](RUNBOOK.en.md#real-closed-loop-and-precise-loading-evidence) and link the materials below to the same sealed index.

Formal verification starts with `freeze_sha256` in the [sign-off template](signoff.template.json). The independent verifier compares it to the SHA-256 of the raw freeze record provided by the independent custodian, then compares `data.tasks_sha256` to the raw bytes of the actual `tasks.json`. Verify that the observation sheet binds to the same task set per [tasks and score sheets](RUNBOOK.en.md#question-sets-and-scoring-tables). Find one row by case ID, scenario, and arm. Recompute the scoring tool's `input_digest` for the input actually delivered in the evidence bundle, compare with that row's `input_sha256`, and verify the same Run in the delivery record. Case IDs and arms can be reused in different batches.

1. **Pin the Run evidence.** An authorized Run owner reads the immutable prefix at the specified position under the [#89 contract](../../docs/contracts/run-verification.md) and keeps the receipt and reference events. Copy Run ID, `through_sequence`, prefix receipt `digest` (as `prefix_digest`), and `basis_sequences` into the index. Verify each basis sequence is a unique positive integer inside the prefix. Preserve the association of each event with exact asset version and source. Provide evidence only within authorized scope.
2. **Seal the original index bytes.** Index those four fields and each material's relative path, SHA-256, byte count, UTC time, collector, evidence type, applicable requirement, execution item, and case ID. After checking file bytes, calculate SHA-256 over the final index's raw bytes and enter `evidence_index.sha256`. Preserve originals and line endings. Verify the index digest and Run prefix digest separately.
3. **Retain original independent sign-off.** The independent verifier uses the established process to confirm the same Run ID, sequence, prefix digest, basis sequences, and index SHA-256 in the original or an expressly referenced attachment. The original also records identity, independence, verification time, scope, judgment, and rationale. Confirm provenance with authorized parties through the existing restricted channel and record the original reference and its own SHA-256. Digests verify bytes. The verifier and original evidence establish independent identity and the basis.
4. **Record owner transcription and receipt separately.** An owner with write permission transcribes the conclusion and basis under the contract. Verify top-level `run_id` and `verification_id`, `through_sequence`, `prefix_digest`, and `basis_sequences` inside `assessment`. Compare `assessment.conclusion` with the independent original. Retain receipt reference, digest, and withdrawal state. The original, index digest, and file references stay in the restricted bundle. Submit the existing strict DTO. The receipt has `evidence_origin:owner_transcribed_external`, `verifier_authentication:unverified_claim`, and `platform_verification:not_performed`. Separately record server preparation, client self-report, observable actual use, and independent judgment. Even when v2 was prepared or the client reported success, actual version used can be UNKNOWN.
5. **Record P6 under the original rules.** Reference the same restricted linkage record in the verified observation row's `evidence` and sign-off `matrix.P6.evidence_refs`. Provide the independent verifier restricted references to the trusted freeze record, the same task batch, and the row. Missing or mismatched bindings cannot enter formal P6. Check whether the index, independent original, and owner receipt bind to the same Run evidence. Record gaps, denials, withdrawals, and inconsistencies. Independent verification aggregates all due cases using existing P6 denominators. PRD A6 and P7 are accepted under their respective criteria. Examples or single pieces of evidence cover only their listed Runs.

The index lists only evidence files preceding sign-off. Keep independent original, receipt, and linkage record separately in the same bundle, with the record binding its own references and digests. File paths are relative to the evidence root. If evidence changes after sealing, create a new index and verification record and retain history. Access to sign-off, files, and Runs follows independent permissions. For denied reads or withdrawn sources, record the visible state without exposing content.

Record unexecuted steps as `NOT_RUN`. Record executed observations that cannot be verified as `UNKNOWN` with a reason. An independent `inconclusive` supported by evidence is a #89 conclusion. Continue recording business outcomes, verification coverage, and sign-off scope per the [execution matrix](RUNBOOK.en.md#execution-matrix) and [PRD measurement rules](PRD-MAPPING.en.md#disclose-metric-differences).

## Public synthetic example

The [linkage record](examples/p6-synthetic/case-link.json) and [index](examples/p6-synthetic/index.json) demonstrate exact digest and field binding. Run UUID, prefix digest, and sequences are synthetic placeholders. The [basis text](examples/p6-synthetic/basis.txt) only verifies file hashing. The independent original and owner receipt are both `NOT_RUN` and excluded from pilot denominators.

From the repository root, check the linkage record, index, and evidence files using the Python standard library.

```sh
python evals/pilot/p6_check.py evals/pilot/examples/p6-synthetic/case-link.json
```

Success means `INDEX_LINKAGE_ONLY`. The tool checks raw-byte SHA-256, file size, case ID and P6 item, duplicate files, and consistent Run prefix fields. It does not read or recompute the Run prefix from a service, check frozen tasks, sign-off originals, owner receipts, or identities, or score. The public example is marked `public_synthetic: true`, must stay `NOT_RUN`, and is excluded from formal results.

Use the linkage record directory as the sealed evidence root. References are `/`-separated relative paths. Absolute paths, `..`, links, and reparse points are rejected. Use only a trusted local offline copy with writes stopped and no concurrent replacement. Matching files do not establish truth or replace formal human review.

## Offline structural verification for each frozen case binding

Run only when the delivery record, independent original, and owner receipt exist. Use the freeze record SHA-256 previously obtained through a trusted channel. Do not calculate it from the bundle under examination and treat that as trusted. Explicitly blocked or contaminated batches are rejected. A matching digest does not prove the freeze conditions were approved. The operator explicitly supplies the freeze record, task set, and observations. Other references are relative to the linkage record directory. The command only reads sealed local offline copies.

```sh
python evals/pilot/p6_bind.py /path/to/package/case-link.json \
  --freeze /path/to/freeze.json --freeze-sha256 "$TRUSTED_FREEZE_SHA256" \
  --tasks /path/to/tasks.json --observation /path/to/observations.json \
  --delivery-ref delivery.json
```

- Store the actual delivered `input` JSON with `case_id`, `scenario`, `arm`, `client`, and `run_id` in the delivery record. Planned input cannot replace actual delivery. Include it in the sealed index as `type: delivered_input` using the actual byte count and SHA-256. The repeat client is fixed as Codex for database troubleshooting and Claude Code for expense auditing. The client that originally produced the Skill is not the no-Skill control for that task. The runbook requires the same client, model, and budget for both arms of a case, checked separately by an independent person. The script checks one row.
- When actual execution exists, set top-level `product_execution` to `RECORDED`. This does not establish completion of other cases or a business judgment. Set the selected row to `COMPLETED`, `ERROR`, or `TIMEOUT`, and place the bundle's linkage filename in `evidence`. The verifier takes row `run_id` from actual delivery and `case_link_sha256` from verified raw linkage bytes. Do not blindly backfill from candidates under examination. Repeated runs of the same case cannot share observation rows incorrectly. The script checks unique case ID/arm, original freeze and task set digests, normalized input digest, and delivered Run.
- When material is complete, mark `status` on the linkage record and both `independent_original` and `owner_transcription` as `RECORDED`. Preserve the original sign-off and individual #89 receipt JSON in original formats and bind raw digests separately. Do not add them to the previously sealed index. Only an explicit null in receipt `withdrawal` permits `withdrawal_status: active` for transcription. Withdrawn, missing, unknown, and unexecuted material cannot pass structural verification.

Successful output is `STRUCTURAL_BINDING_ONLY`. It verifies receipt Run and verification IDs, the prefix tuple, provenance flags, and the stored withdrawal field. `passed`, `failed`, and `inconclusive` are transcribed claims and do not alter structural results. The #89 receipt does not contain the independent original's digest. The tool checks both raw digests separately without interpreting the original's conclusion, identity, or signature, and does not verify sign-off references, latest receipt state, current source visibility, or authoritative prefix content. The public `NOT_RUN` example supports only the prior index check. Formal human review, scoring, and independent sign-off follow the established workflow.
